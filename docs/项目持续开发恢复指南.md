# PyPMXVMD 项目持续开发恢复指南

## 1. 文档用途

本文是项目从远程仓库恢复后的执行状态账本。它记录已经恢复且实际验证过的能力、当前开发约束和下一阶段任务，避免把计划、文件存在或测试跳过误认为项目能力已经恢复。

开始开发前先阅读 `.agents/README.md`。完成一项恢复任务后，应同步更新本文中的验证命令、结果和剩余风险。

## 2. 当前决定

- 项目统一使用 uv 管理解释器、依赖、命令和构建，不直接使用 pip，不手工操作虚拟环境。
- 开发和发布基线统一为 Python 3.11，本机由 `.python-version` 固定为 `3.11.12`。
- 不把外部备份和测试语料入库作为恢复工作的阻断条件，直接推进缓存治理、Cython、测试、CI、打包和文档。
- `tests/data/test_models` 与 `tests/data/test_vmds` 是本地真实语料，默认不进入发布包；测试发现语料后逐文件执行。
- 性能 benchmark 只作为趋势信息。正确性、构建和产物校验才是当前阻断项。

标准环境命令：

```powershell
uv sync --group dev --python 3.11.12
uv run --python 3.11.12 --no-sync pytest -m "not benchmark" -ra
```

当前 shell 可能设置了 `UV_PYTHON=3.11` 和 `UV_NO_SYNC=true`。项目命令显式指定解释器并按需先执行 `uv sync`，不修改用户全局环境。

## 7. 下一阶段：PMX 完整支持

公共 `load_pmx()` 现已 fail closed：当前实现只加载到 Material 时会抛出
`IncompletePmxError`。需要检查旧字段的调用方必须显式使用 `load_pmx_partial()`，并通过
`PmxParseReport` 查看已加载 section、最终偏移、文件长度、尾部字节和缺失 section。
公共 `save_pmx()` 同样已 fail closed，在完整 writer 交付前抛出
`IncompletePmxWriterError`，且不创建目标文件；旧 serializer 仅作为显式测试工具保留。
7 个真实模型已逐文件证明 Material 后仍有未消费数据；这不代表 PMX 2.0/2.1 已经完整、
无损支持。详细路线见 [PMX 支持改进计划](./PMX支持改进计划.md)。

W1 二进制安全层也已完成：活动 Python reader 使用 `PmxCursor`，统一 little-endian、
边界、字符串/count 上限、有符号 index 和 section/offset 异常；`auto` 固定选择该安全
路径，显式 Cython 运行前先完成 Cursor 探测。下一阶段为 W2 PMX 语义模型补全。

W2 已开始但尚未关闭：Header 及用户优先的 Bone、Rigid Body、Joint、Material 模型
字段和字段级 validator 已补齐第一批；Morph/Display Frame 与完整 reader/writer 仍未完成。

执行顺序：

1. `[已完成 W0]` 冻结不完整公共读写并建立 section/offset/trailing bytes 证据。
2. `[已完成 W1]` 建立 little-endian Cursor、资源上限和二进制布局回归。
3. `[下一步 W2]` 补全 PMX 2.0 语义模型、兼容字段和 validator。
4. 完成 canonical writer，并只对 `tmp_path` 中的副本做真实语料 round-trip。
5. 增加 PMX 2.1、QDEF 和 Soft Body。
6. 对齐 fast Python 与 Cython，最后才恢复性能优化。

writer 未通过对应字段级验收前，不覆盖任何真实模型原件，也不宣称完整 PMX 读写支持。

## 10. 持续开发规则

1. 依赖和命令统一通过 uv，不直接使用 pip。
2. 默认运行 `not benchmark` correctness 集；benchmark 不以单次耗时作为发布门槛。
3. 修改 parser/model/writer 时必须同时补充回归测试。
4. 对真实文件的写入测试只能操作 pytest 临时目录中的副本。
5. Cython 优化必须先与标准实现做字段级 parity。
6. 每次阶段性恢复后更新本文的实际命令和结果，未验证项不得勾选。
